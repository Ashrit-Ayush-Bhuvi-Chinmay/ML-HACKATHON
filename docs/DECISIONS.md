# Decisions log

Each entry: what we decided, why, and where the evidence lives. Dates are 2026-11-18.

| # | Decision | Why | Evidence |
|---|---|---|---|
| 1 | Work in metres in a per-trip UTM projection (zone of the track's median point). | Trips span several continents; degree distances are not metric. UTM is conformal with < 0.1 % scale error inside a zone. | `src/pathsnap/geo.py` |
| 2 | Derive one reference arc per GPS point by **monotonic DP alignment** of the track to the route (capped distance + heading penalty). | `.route` is only an ordered list of arcs; there is no per-point label. Monotonic order handles loops and repeated arcs (10 routes, up to 255 repeats); the heading term separates the two directions of a road (92 % of arcs have a reverse twin). | `src/pathsnap/labels.py`, `results/labels/labels_summary.csv` |
| 3 | Points more than **50 m** from their reference arc are unlabelled; trips with a median label distance above 50 m are excluded (train 33, train 54). | Typical label distance is 4–7 m (p99 on student-test 28 m). Trip 33's GPS is on roads but its route is ~120 m away (reference error); trip 54's whole track sits ~117 m off every road (coordinate offset). Both rules were set from train data. | `results/labels/labels_summary.csv` |
| 4 | Candidates: directed arcs within **50 m**, at most **16** per point. | Radius/K sweep on train: miss rate 0.11 % at ~7.8 candidates per point; a larger radius adds no reliable labels. | `results/candidates/sweep.csv` |
| 5 | The nearest-arc rule is the baseline to beat. | It is right for only 55 % of points but the reference is within the nearest two for 91 %. The gap is direction (twin arcs), so heading features matter most. | `results/candidates/ref_rank.csv` |
| 6 | Cross-validation is grouped by **trip** (5 folds, seed 352). | Points of one trip are strongly correlated; splitting by point would leak. | `scripts/04_compare_models.py` |
| 7 | Primary selection metric: **observation-level Top-1** on reliably labelled points (misses count as errors). Macro F1 and log loss are reported at pair level. | The decoder uses the ranking of candidates, not a 0.5 threshold. Log loss matters because probabilities become HMM emissions. | `src/pathsnap/evaluate.py` |
| 8 | Route continuity = share of consecutive predicted-arc changes that are **physically reachable** over the network (≤ max(3 × GPS distance, 100 m)), within an evidence segment; `null` with the transition count when there is nothing to judge. The strict head-to-tail check is still reported but named `strict_adjacency`. | Strict adjacency penalises correct predictions: at 1 Hz, consecutive points often skip short arcs (only 91 % of reference arcs get a point at all). A fully unmatched trip used to score 1.0 continuity; "nothing to judge" is now `null`. | `src/pathsnap/hmm.py`, `src/pathsnap/evaluate.py` |
| 9 | HMM decoder parameters are tuned on **train out-of-fold** predictions only. | The decoder must not see probabilities the classifier was trained on, and student-test stays a clean comparison set. | `scripts/05_hmm.py`, `results/hmm/` |
| 10 | Add a **long-range heading** (points ≥ 40 m apart, within ±180 s) next to the short one (feature set v2: 29 features; v1 had 26). | Error analysis: accuracy was 51 % below 1 m/s and 61 % at 1–3 m/s, mostly wrong-direction (twin) errors, because a stopped car has no usable short-range heading. With v2, LightGBM student-test Top-1 went 0.889 → 0.930, log loss 0.062 → 0.048. All models were re-run on v2 for the comparison. | `scripts/08_error_analysis.py`, `results/errors/`, `results/models/model_comparison_featureset_v1.csv` |
| 11 | Use the classifier's probabilities as HMM emissions (β and emission weight tuned per model on train OOF predictions of 30 train trips). | Student-test, feature set v2, LightGBM: Top-1 0.930 → 0.948 with the HMM, plausible continuity 0.904 → 0.995, sequence F1 0.812 → 0.985, coverage F1 0.922 → 0.988. The classic distance-only HMM reaches Top-1 0.908 and sequence F1 0.968, so the learned emission helps. XGBoost (0.947) and the listwise ranker (0.943) as emissions give the same picture. (An earlier v1-feature run with the old metric definitions is superseded.) | `results/hmm/summary_*.csv`, `results/hmm/per_trip_*.csv`, `results/hmm/tuning_*.csv` |

| 12 | A label-free **GPS-offset correction** was built and then **disabled**; only its diagnostic (median distance to the nearest road, `gps_looks_offset`) is reported. | Only one supplied trip is offset (train 54: 84 m; every other trip ≤ 7.3 m). On it, the grid-searched shift fitted the wrong streets of a dense grid (median misfit 3.5 m), and route F1 fell from 0.947 to 0.133. Without correction the HMM already recovers the route (F1 0.947). It never triggers on normal trips. | `scripts/11_offset_check.py`, `results/pipeline/offset_check.csv` |
| 13 | The pipeline is hardened for unseen evaluator trips: flat or sub-folder layout, unsorted timestamps, missing `.route` (predict only), no road within reach, single-point trips; non-finite metrics become `null`. | The evaluator's ten trips are unseen, and a crash during the demo costs more than any accuracy point. | `scripts/09_robustness_check.py` |

| 14 | Report two route scores: **coverage F1** (length-weighted overlap of arc *sets*) and **sequence F1** (length-weighted longest common subsequence of arc *sequences*). | Set overlap ignores travel order and repeated laps: an extra lap, a missed lap and a reversed route all score coverage F1 = 1.0, but sequence F1 = 0.667 / 0.667 / 0.333. The brief asks for sequence-level performance. | `src/pathsnap/evaluate.py` |
| 15 | Route assembly respects GPS gaps: a new route piece starts wherever the decoder starts a new chain (dt > 60 s or jump > 1 km). | Previously, decoded pieces were re-joined by shortest paths, drawing a continuous line across e.g. a 42.5 h gap with no evidence. Trips 90 and 78 now return 2 pieces each. | `src/pathsnap/hmm.py` (`segment_ids`, `build_route`) |
| 16 | Fixes from an external code review (2026-11-18): empty road corridor crashed `RoadGraph` (now returns all points unmatched); the robustness script now asserts expectations, checks strict JSON, and exits non-zero on failure; `timings_ms.total` is the true wall clock. | Demo reliability and honest reporting. | `scripts/09_robustness_check.py`, `src/pathsnap/pipeline.py` |

| 17 | **Bayesian optimisation** of LightGBM with Optuna TPE (objective: 3-fold trip-grouped CV Top-1 on train; median pruner; 40-minute cap). | 11 trials: trial 0 = untuned configuration, trials 1–7 random warm-up, 8–10 TPE-guided (one pruned). Best = guided trial 8 (0.93585 vs 0.93486 untuned). Same 5 folds and student-test for tuned vs untuned: CV Top-1 0.9356 → 0.9365, test Top-1 0.9301 → 0.9323, CV macro F1 0.9600 → 0.9598, log loss 0.0490 → 0.0492; inference about 3× slower (800 trees × 250 leaves). Small gain: the model is limited by its features, not its hyperparameters. | `results/tuning/trials_lightgbm.csv`, `results/tuning/optuna_lightgbm.db`, `results/models/model_comparison.csv` |
| 18 | **Final model: Bayesian-tuned LightGBM + HMM**, exported from the exact saved comparison model (no refit). | On train evidence the boosting models tie: HMM Top-1 on train OOF (30 trips) is 0.9414 for LightGBM, 0.9417 for XGBoost and 0.9354 for the listwise ranker; CV Top-1 is 0.9356 / 0.9361 / 0.9361 for LightGBM / XGBoost / CatBoost (fold std ≈ 0.012). LightGBM is the model the tuning was applied to, and it runs on CPU only (the API laptop may have no CUDA). | `docs/FREEZE.md`, `artifacts/pathsnap_model.joblib` |
| 19 | **Freeze before the evaluator data arrives**: final bundle, all saved models and the code commit are hashed in `docs/FREEZE.md`; afterwards the API only points `PATHSNAP_EVAL_DIR` at the evaluator folder. | The rules forbid any fitting, tuning or selection on evaluator data; the hashes and commit time make that verifiable. | `scripts/13_freeze.py`, `docs/FREEZE.md` |
